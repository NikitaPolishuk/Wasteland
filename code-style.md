# Стиль C# — Wasteland

Эти правила применяются к новому и изменяемому рукописному C#-коду в `Assets/_Project/Scripts/`. Не переформатируй несвязанные участки существующих файлов ради приведения их к этому стилю.

Правила не распространяются на сторонний код и сгенерированные файлы, в частности код плагинов в `Assets/Plugins/` и wrapper Input System в `Assets/_Project/Input/KeyBoardInput_Actions.cs`. Сохраняй их без стилевых правок.

## Структура файла и класса

- В новых классах располагай члены в порядке: события и поля, конструктор, свойства, методы. Внутри каждой группы располагай члены в порядке `public`, `protected`, `private`.
- Пиши модификатор доступа явно, кроме членов интерфейсов, где `public` подразумевается.
- События размещай перед остальными полями. Именуй события в прошедшем времени (`Killed`, `Damaged`), обработчики — `OnX` (`OnKilled`).
- Для namespace повторяй схему ближайшего кода в той же области. В проекте используются `Assets.Scripts...`, `Assets.ScriptableObjects` и `Assets.Installer`; не добавляй префикс `_Project` из стороннего примера.

## Именование

- `camelCase` — параметры и локальные переменные.
- `_camelCase` — приватные поля; `PascalCase` — публичные и защищённые поля, свойства, методы, типы и namespace.
- `UPPER_SNAKE_CASE` — константы. Для `readonly`-полей используй стиль имени поля с учётом модификатора доступа: например, `_inputActions` для приватного поля.
- Называй булевы методы и свойства по смыслу через `Is`, `Can` или `Has`. Методы вида `TryX(...)`, возвращающие `bool`, используй для операций с явным результатом успеха.
- Выбирай точные имена, существительные для типов и значений, глаголы для действий; используй множественное число для коллекций и избегай тавтологии и ненужных сокращений.
- Не выбирай размытые имена вроде `Helper` или `Manager`, если ответственность можно назвать точнее. Не переименовывай существующие типы только ради этого правила.

## Форматирование

- Используй явные типы вместо `var`, в том числе в `foreach` и при `out`-переменных.
- Для проверки булева значения на ложь пиши `value == false`, а не `!value`.
- Не ставь более одной пустой строки подряд. Отделяй пустой строкой логические блоки и управляющие конструкции от соседнего кода; в `switch` разделяй блоки `case` пустыми строками.
- Сохраняй отступы и расстановку скобок в стиле ближайших файлов проекта, если задача или используемый форматтер не задают иное.

## Содержимое

- Не оставляй магические числа: выноси значения в именованные константы, сериализуемые поля или подходящие `ScriptableObject`-конфиги. Литерал `0` допустим, когда его смысл очевиден из выражения.
- Убирай дублирование, вынося повторяющуюся логику в метод с точным именем.
- Пиши логи с понятным контекстом и готовыми значениями; не прячь вычисления в текст сообщения.

## Асинхронный код

- Перед добавлением асинхронного кода проверь уже используемые в проекте API и зависимости. Не добавляй UniTask или другую библиотеку только ради следования этому документу.
- Для асинхронных методов используй суффикс `Async` и тип возврата, принятый фактически используемым API.
- Не используй `async void`, кроме обработчиков, чья сигнатура требует `void`; в таких обработчиках перехватывай и обрабатывай исключения.
- Если API принимает `CancellationToken`, ставь его последним параметром и передавай во вложенные асинхронные вызовы.
